# Q6/Q7: Screen Share Rendering Failure — Raw Element Test + Local/Remote Determination

## Q6: Raw Element Test Protocol

### Objective
Determine whether a published screen share MediaStreamTrack is viable at the raw DOM element level, independent of app-level rendering filters. This isolates track health from UI/app rendering decisions.

### Test Steps
1. **Capture the published screen track** from `localParticipant.screenTracks` or `publications.get(trackId)` after `startScreenShare()` completes.
2. **Create a bare video element**: `const vid = document.createElement('video');`
3. **Attach the track to a MediaStream**: `vid.srcObject = new MediaStream([track]);`
4. **Set attributes**: `vid.muted = true; vid.playsInline = true;`
5. **Play the element**: `vid.play();`
6. **Log the following at regular intervals (e.g., every 100ms for 3s)**:
   - `vid.readyState` (should progress from `0` → `HAVE_METADATA` → `HAVE_CURRENT_DATA` → `CAN_PLAY` → `PLAYING`)
   - `vid.videoWidth` (should stabilize > 0 once track is viable)
   - `vid.onplaying` fire (if track is live and rendering)
   - `vid.onerror` fire (if track is broken or unsupported)
   - Console logs of `LocalTrackPublished` event presence/absence

### Expected Pass/Fail Interpretation

| Outcome | readyState | videoWidth | onplaying | onerror | Interpretation |
|---|---|---|---|---|---|
| **PASS** | ≥ `HAVE_CURRENT_DATA` (2) stabilizes | ≥ 1 pixel (e.g., ≥ 160×90 for screen share) | Fires within 3s | Never fires | Track is live and renderable at the element level. If the UI does not display it, the issue is **app filtering** (e.g., ControlBar not calling `startScreenShare()`, `publications` not registered, or SFrame transform blocking), not the track itself. |
| **FAIL — Track Dead** | Stuck at `0` (UNINITIALIZED) or never reaches `2` | 0 or very small (≤ 10px) | Never fires | `vid.onerror` fires | The track itself is bad — no media data being generated by `getDisplayMedia`. This is a **track-level failure** (permissions denied, capture device unavailable, browser limitation). |
| **FAIL — App Filtering** | Progresses normally (≥ 2) | Stabilizes > 0 | Fires | Never fires | Track is healthy and renderable. The issue is **upstream app logic** — e.g., `publications.size` not incrementing, ControlBar not wiring `startScreenShare()`, `screenSharing` store state not updating, or SFrame/E2EE encrypting the track so it appears "black" in plaintext view. This is the **H4 check** referenced in the defect: H4 verifies that the track is live but app-filtered. |
| **FAIL — Browser/Format** | Progresses but `videoWidth` stalls at low resolution | Very small, intermittent | Fires intermittently | May fire due to unsupported format | Browser or format incompatibility (e.g., Safari H264 baseline vs VP9 simulcast). Requires browser-specific workaround. |

### Q6 Evidence Checklist
- [ ] `console` — `LocalTrackPublished` event presence/absence (before/after share start)
- [ ] `console` — `track.onmuted`, `track.onended`, `track.onunmuted` state changes
- [ ] `console` — `readyState` timeline (screenshotted or logged over 3s)
- [ ] `console` — `videoWidth` values over time
- [ ] `console` — `onerror` events (if any)
- [ ] `console` — `onplaying` fire time
- [ ] `chrome://webrtc-internals` — publication size check before/after share start
- [ ] Wireshark `rtp && sframe` pcap (if SFrame enabled) — verify ciphertext vs. plaintext
- [ ] Publication source: `localParticipant.getScreenSharing()` store state, `setLocalScreenShare` call path

## Q7: Local-Only vs Remote-Too Determination

### Objective
Determine whether a second participant (remote) sees the screen share render locally or remotely. This verdict logic decides if the screen share issue is isolated to the local participant or affects the entire session.

### Test Steps (Second Participant)
1. **Second participant joins the same room** via a separate browser/tab or user profile with a different `participantId`.
2. **Verify remote TrackSubscribed event**: Listen for `trackSubscribed` on the remote connection for the screen share source track. Capture:
   - `track` object (kind: 'video')
   - `track.readyState` (should be `'live'`})
   - `track.label` (should match screen share device label)
3. **Check remote renders**: Observe whether the remote participant's video grid displays the shared screen. If using a VideoGrid component, verify the `remoteStreams` contains the screen share track.
4. **Capture remote WebRTC stats**: Open `chrome://webrtc-internals` (or browser equivalent) on the second participant's side and capture:
   - Inbound SSRC for the screen share track
   - `googTrackId`, `googListenerId`
   - `codecName` (VP9/H264)
   - `fractions_lost`, `packets_sent`, `packets_received`
5. **Verify remote inbound rendering**: On the second participant, render the remote track to a bare video element (same Q6 protocol) to confirm the remote can decode/render the stream.
6. **Check for `trackPublications` on local host**: On the host, verify `publications.size` increased after screen share start, and that the published track is accessible.

### Verdict Logic

| Verdict | Evidence Captured | Logic |
|---|---|---|
| **LOCAL ONLY** | - Second participant's `trackSubscribed` **does NOT fire** for screen share track<br>- Second participant's `chrome://webrtc-internals` shows **no inbound SSRC** for screen share<br>- Second participant's bare video element: `readyState` stalls at 0, `videoWidth` = 0<br>- Host's `publications.size` may or may not have incremented (dependent on wiring) | The screen share track was **not distributed** to remote participants. Issue is in the **local publishing path** only (e.g., `startScreenShare` not called, `setScreenShareEnabled` not wired, `publications` registry not updated). The remote peer never received the track. |
| **REMOTE TOO** | - Second participant's `trackSubscribed` **fires** for screen share track<br>- Second participant's `chrome://webrtc-internals` shows **inbound SSRC** with valid codec<br>- Second participant's bare video element: `readyState` progresses to ≥ 2, `videoWidth` > 0, `onplaying` fires<br>- Host's `publications.size` incremented correctly | The screen share track was **successfully published and distributed**. The issue is **not local-only**; both local and remote participants are affected. This points to a shared resource (e.g., SFrame transform, SFU encoding, TURN relay, or browser compatibility). |
| **INDETERMINATE** | - `trackSubscribed` fires but remote video is black/broken<br>- Inbound SSRC present but `codecName` mismatched or `fractions_lost > 0` | Track was distributed but **decoding/rendering failed** remotely. This could be SFrame blind-forward mismatch, codec incompatibility, or SFU Last-N/dynacast issue. Requires further SFrame/encoding investigation. |

### Q7 Evidence Checklist
- [ ] `console` — `trackSubscribed` event fire time and track properties (remote participant)
- [ ] `console` — `track.readyState` value on remote track ('live' vs 'ended')
- [ ] `chrome://webrtc-internals` — inbound SSRC for screen share track (remote participant)
- [ ] `chrome://webrtc-internals` — codecName, fractions_lost, packets_received
- [ ] Second participant's bare video element: `readyState`, `videoWidth`, `onplaying`, `onerror` (Q6 protocol)
- [ ] Host `publications.size` before/after screen share start
- [ ] `localParticipant.getScreenSharing()` store state value
- [ ] `setScreenShareEnabled(true/false)` call path verification
- [ ] SFrame transform status: `sframeRef.current` installed? encrypt counter active?
- [ ] Browser matrix: which browsers show LOCAL ONLY vs REMOTE TOO

### Severity Input
- If **LOCAL ONLY**: P2 — verify app wiring (`ControlBar.handleScreenShare()` → `useWebRTC.startScreenShare()`). This is a code-separation bug.
- If **REMOTE TOO**: P1 — shared infrastructure issue (SFrame, SFU, TURN). Affects all participants.
- If **INDETERMINATE**: P1 — decoding/rendering mismatch. Requires SFrame/histogram investigation.
